# agent-wake-poll pitfalls

只在 `ACTION=hang`、或怀疑「进度不动但不知道 job 死没死」时读。都是实际把 agent 空转过几小时的情形。

## 假存活：活性探测命中了自己

**症状**：`pgrep` 每轮都说进程在，但产物几小时不涨；`retry` 永不触发，队列静默空转到早上。

**原因**：你的检查命令是 agent 用 `/bin/bash -c '…pgrep -f "train.py"…'` 跑的，
这个包装 shell 的命令行**本身就含 `train.py`**，于是 `pgrep -f 'train.py'` 恒命中它自己。
死掉的 job 因此永远显示存活，hang 判据里「进程不在」这个条件不可能成立。

**做法**：模式加锚点或绝对路径前缀，让包装 shell（以 `/bin/bash` 开头）不可能匹配：

```bash
pgrep -cf '^python /abs/train\.py' || true
ps -eo args= | grep -E '^python .*/train\.py' | grep -v grep
```

同一个机制也会咬 `pkill -f '<含 tag 的串>'`：它会连包装 shell 一起杀，
表现是那个 Shell 立刻 `status: error`，之后再没有任何 wake。**停 wake 只用 `wake.py stop`。**

## GPU util 不是活性证据

**症状**：`nvidia-smi` 显示 util 100%，判定「在跑」，但其实是占卡脚本在跑，真 job 早挂了。

**做法**：看**显存量级**（推理满载 vs 纯占卡差一个数量级）、产物计数、log mtime；util 只能证明「有人在用卡」。

汇报里的「显卡利用率」（近 1h 采样均值，仅本机）同理：它是**吞吐/占用效率**指标，
用来看这段时间卡有没有闲着、要不要调 batch，不能用来判断 job 是否还活着。

## 首条产出前的空睡

**症状**：`metric_now` 一直 0，每轮都按「还没开始产出」继续睡，几小时后才发现是缺依赖 / 权限 / NCCL 起不来。

**原因**：环境类失败（依赖缺失、MPI/NCCL、OOM、路径权限）几乎全都在第一条产出之前爆，
而这个阶段度量恒为 0，光看度量分不出「正常预热」和「已经死了」。

**做法**：`metric_now==0` 时 delay 固定 120s（脚本已保证），每轮另外确认三件事都在动：
进程存活（锚定模式）、log mtime 在推进、阶段/前置度量在涨。任一停滞就当 stall 取证，别继续睡。

## 度量命令本身把集群拖死

KFS 等共享存储上，`find` 无界递归会给元数据集群造成压力、进程进 D 状态。
优先数 log：`grep -c 'Combining:' /abs/run.log`。必须 find 时限定 `-maxdepth` 和子目录。

## metric 混了两个阶段的产物：ETA 在前一阶段被系统性高估

**症状**：进度百分比看着正常，但「预计完成」比手算晚十个小时；等后一阶段的产物落盘，ETA 又猛地跳回来。

**原因**：`metric` 把先后两个阶段的产物加在一起（实测：每个变体先花 4h 出 100 个 latent，
再在 5 min 内爆出 100 个 mp4）。ETA 是线性外推的，前一阶段只看得见一半产物，
速率被高估近一倍 —— 600 的目标把 09 点算成了次日 17:31。

**做法**：`--metric-cmd` 只数**占绝大部分墙钟的那个阶段**（例子里是 latent，目标 300），
另一阶段交给 `--report-cmd` 单独报。后一阶段卡住时前一阶段也会停（下一轮不开工），停滞判据不会漏。

## 产物按批次爆发落盘：批与批之间被判成 hang

**症状**：`ACTION=hang`，但 log tail 里进度条正在推进、显卡利用率 99%。
实测：32 例分 2 批跑，metric 数 latent，第 1 批 16 个一次性落盘后就卡在 16/32 八分钟，
连记两轮停滞触发 hang；此时第 2 批去噪正走到 31/50、15.45 s/it。

**原因**：`--metric-cmd` 数的产物在**批内不产出**。停滞判据看的是度量涨不涨，
而这个度量的分辨率等于批大小，两批之间必然有一整批的墙钟纹丝不动。
「只数占绝大部分墙钟的那个阶段」还不够——那个阶段自己也得在阶段内逐步产出。

**做法**：选**批内每分钟都在动**的量。批式推理可以数去噪步数，把已完成批次折算进去：

```bash
# 已完成批次 × 每批步数 + 当前批进度, 单调且约 15s 一跳
done=$(( $(find "$O" -path '*/video_latent/*' -type f | wc -l) / 16 * 50 ))
cur=$(grep -oE '\| [0-9]+/50 \[' "$LOG" | tail -1 | grep -oE '[0-9]+' | head -1)
echo $(( done + ${cur:-0} ))
```

真产物计数交给 `--report-cmd`。误报当下**不要 retry**：重跑会把已烧掉的整批去噪作废，
先按 log tail 的进度条和 util 确认活性，再 arm 跨过这一批。

## 换了对象却没 `started`：ETA 按上一个对象的起点算

**症状**：`check` 的进度是对的，但「预计完成」比手算晚十几个小时，`已用/剩余` 也离谱
（实测：当前变体约 1 小时后出片，汇报写成次日 16:54，已用 11h12m）。

**原因**：同一个 tag 换跑下一个单元 / 变体时只改了 `metric_cmd`，`started_at` 还是上一个对象的。
速率 = 新产物数 / 上一个对象至今的墙钟，分母虚高十几倍，ETA 跟着飘。

**做法**：换对象、重跑都要 `wake.py started --tag TAG`（重置 `started_at` 与 `metric_*` / `stall_count`）。
汇报里「速率」明显偏慢、或 ETA 与 `下次检查` 的量级对不上，先查 `started_at` 是不是上一个对象留下的。

## 文件存在不等于写完：metric 虚报，下游读到半成品

**症状**：metric 报某阶段 8/8 已完成，下一阶段一起来就全部 rank 崩在 `torch.load`：
`PytorchStreamReader failed reading zip archive: failed finding central directory`。

**原因**：上游用后台线程写盘（例:`--use_thread_write`），主函数打完 `main total` 就返回，
写盘还在继续（实测又写了 3 分钟）。这段时间里 8 个文件都已存在但只有 2 个写到了最终大小，
按「文件数」判完成的 metric 和交接判据同时被骗过，128 个 rank 读到截断的 zip 全崩，
白烧一次转换（13 分钟）加一次启动。共享存储上还更隐蔽：`close()` 之后数据可能仍在回写。

**做法**：完成判据按**内容**而不是**存在**，两条一起用：

```bash
# 同批分片大小必须全部相同（缺一片或半截都不通过）
full=$(find "$O" -maxdepth 1 -name 'model_8_*.ckpt' -printf '%s\n' | sort -rn | head -1)
[ "$(find "$O" -maxdepth 1 -name 'model_8_*.ckpt' -size "${full}c" | wc -l)" = 8 ]
```

再加一轮**稳定性**确认：隔 15s 采两次大小快照，两次一致才放行下一阶段。
上游进程退出也不算完成信号——退出的可能只是主进程，写盘线程或 fork 出的子进程还在。

## 占卡在运行中被拉回来

**症状**：任务确实在跑，但速度慢得离谱（实测去噪 100 s/it，正常 19.8 s/it，5 倍），
并行度、卡数、配置都对得上，日志也没有报错。

**原因**：占卡进程会在每张卡上烧 SM，和真任务抢算力。启动前放掉了，但上一个 runner 被杀时
它的 `trap ... EXIT` 又把占卡兜底拉了回来，于是推理全程带着占卡跑。

**做法**：把放占卡写进启动脚本本体（不是只在外面手放一次），并且每轮 `check` 都确认占卡进程为 0。
速率明显低于同型任务的历史值时，先查占卡，别先怀疑并行度或数据。

## 跨 session 失联

wake 绑当前 Cursor 会话。会话关掉后 `sleep` 可能还在，但没人消费那条 `AGENT_LOOP_WAKE_*`。
不是故障：用户回来说「wake poll」，直接从 `check` 继续，state 在磁盘上没丢。
